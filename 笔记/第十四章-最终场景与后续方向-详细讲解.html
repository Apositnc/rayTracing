14.1② 用一个大球当“平地”

先用生活里的话说：地球是圆的，但你站在小操场上感觉地面很平。我们也用一个超大的球，只拍它顶部的一小块，看起来就像一片地板。
C++ · 对照你的项目变量名
auto ground = make_shared<lambertian>(color(0.5, 0.5, 0.5));
world.add(make_shared<sphere>(point3(0, -1000, 0), 1000, ground));

球心在 y=−1000，半径为 1000，球顶刚好到 y=0。小球半径是 0.2，所以把它们球心放在 y=0.2，球底也到 y=0，视觉上像放在地面上。

它真的完全平吗？

并不是。离中心越远，球面会略微下弯。若离竖直轴的水平距离为 ρ，球面高度为：

y = −1000 + √(1000² − ρ²) 当 ρ 比 1000 小很多时：y ≈ −ρ²/2000 ρ=4 → y≈−0.008 ρ=10 → y≈−0.05

所以教材的小球并不在每个位置都严格与大球接触。这种近似在该构图中方便、够用；若你研究精确接触或放大的近景，就要考虑真正的平面/四边形，或按大球表面高度摆放。

color(0.5,0.5,0.5) 是材质的线性反射率参数。它不保证最终输出像素恰好是 (128,128,128)，因为照明、反弹与 gamma 变换都会参与最终颜色。

14.1③ 双重循环：给地面划 22 × 22 个格子

先用生活里的话说：在地上画一个大棋盘。外层循环决定走到哪一列，内层循环把这一列中的所有格子挨个访问。每到一个格子，我们决定放什么球。
C++ · 对照你的项目变量名
for (int a = -11; a < 11; ++a) {
    for (int b = -11; b < 11; ++b) {
        // 处理格子 (a, b)
    }
}

a 的取值是 −11、−10、……、9、10，一共 22 个；b 也一样。所以最多检查 22×22=484 个候选格子。条件是 <11，没有访问 11；不是 23×23。

这两个变量对应世界的 X 和 Z 方向，因为地面展开在 XZ 平面；Y 留给“高度”。不要把棋盘上的第二个变量 b 误写进 Y，造成一面竖着的球墙。

C++ · 对照你的项目变量名
point3 center(a + 0.9 * random_double(), 0.2,
              b + 0.9 * random_double());

若 a=2、b=−3，两个随机数分别为 0.4 与 0.7，球心就是：

x = 2 + 0.9*0.4 = 2.36 y = 0.2 z = −3 + 0.9*0.7 = −2.37 球心 = (2.36, 0.2, −2.37)

随机偏移让每个小球不再像士兵一样排成直线，但仍然保留棋盘式分布。每格只选一个候选球心，并不是把所有球在整个地面上完全独立乱撒。

0.9 不是“保证小球不碰撞”的常数。相邻格子的球心可能只差约 0.1，而两个半径 0.2 的球要相距至少 0.4 才不重叠。教材场景允许部分小球重叠；如果要严格互不相交，需要额外检测。

14.1④ 留出空位：距离判断到底保护了什么？

先用生活里的话说：广场里有一位很重要的大金属球。我们在它附近放一张“这里少摆些小玩具”的纸条，遇到离这个标记太近的小球就跳过。
C++ · 对照你的项目变量名
if ((center - point3(4, 0.2, 0)).length() > 0.9) {
    // 离标记点足够远，才创建小球。
}

center 与标记点的 y 都是 0.2，所以相减后 y 分量为 0。这个判断实际测量的是 XZ 平面里的水平距离。若距离 ≤0.9，该候选球不加入 world。

例如 center=(4.3,0.2,0.4)，位移=(0.3,0,0.4)，距离=√(0.09+0.16)=0.5，小于 0.9，所以跳过。若 center=(5.2,0.2,0)，距离=1.2，则保留。

它是不是完整的防碰撞系统？

不是。它只检查一个标记附近，不检查所有小球之间，也不检查另外两个大球周围。右侧排除区的尺寸也是针对这里的球半径选定的，不能直接推广到任意场景。

右侧大球：中心 (4,1,0)，半径 1 小球：中心高度 0.2，半径 0.2 竖直间距 = 0.8 要严格不重叠：水平距离² + 0.8² ≥ (1+0.2)² 水平距离 ≥ √0.8 ≈ 0.894427

对于这个右侧大球，教材采用 0.9 的水平排除半径，略大于 0.8944，确实足以避免这些小球与它重叠（按理想球几何）。但它仍不是对整个场景的普遍碰撞处理。这也是为什么不能把 0.9 当成“每两个球都安全”的保证。

14.1⑤ 随机选材料：80%、15%、5%

先用生活里的话说：把 100 张小纸条放进盒子：80 张写“橡皮球”，15 张写“金属球”，5 张写“玻璃球”。每次摸一张，决定新球穿什么衣服。程序用 0 到 1 之间的随机数完成同样的选择。
C++ · 对照你的项目变量名
double choose_mat = random_double();
if (choose_mat < 0.8) {
    // [0, 0.8)：漫反射
} else if (choose_mat < 0.95) {
    // [0.8, 0.95)：金属
} else {
    // [0.95, 1)：玻璃
}
随机数区间区间长度材质概率例子
[0,0.8)0.880% 漫反射0.12、0.79
[0.8,0.95)0.1515% 金属0.80、0.91
[0.95,1)0.055% 玻璃0.95、0.99

第二个条件不是“95% 的球是金属”。能走到 else if 的数，已经被前一个条件排除了小于 0.8 的部分。因此金属区间只有 0.95−0.8=0.15。

概率是长期平均，不是配额。一次生成 480 颗小球，不保证恰好 384 颗漫反射、72 颗金属、24 颗玻璃；就像抛 10 次硬币不保证正好 5 次正面。

三个分支共享一个材料变量

C++ · 对照你的项目变量名
shared_ptr<material> sphere_material;
// 在分支里赋值为 lambertian、metal 或 dielectric。
world.add(make_shared<sphere>(center, 0.2, sphere_material));

shared_ptr<material> 可以保存指向不同派生材质的共享指针。球里存的是同一个材料对象的引用关系，命中后通过虚函数 scatter() 执行实际材质行为。离开本次循环后，本地变量销毁了，但球仍持有共享指针，所以材质不会立刻消失。

教材在每个分支里都写一遍 world.add；本讲解把这句移到分支之后，减少重复。三个分支都一定赋值，生成场景的逻辑一致。

想一想：choose_mat 恰好为 0.8 时选哪种材料？

14.1⑥ 同样是随机颜色，为什么写法不同？

漫反射：两个随机颜色按分量相乘

C++ · 对照你的项目变量名
color albedo = color::random() * color::random();
sphere_material = make_shared<lambertian>(albedo);

你的 vec3 重载了两个向量相乘，结果是对应分量相乘，不是点积，也不是叉积。

(0.8,0.2,0.6) * (0.5,0.9,0.3) = (0.4,0.18,0.18)

两个 [0,1) 的数相乘通常会更小，因此颜色偏向较暗、较深。理想独立均匀随机数 U、V 各自平均为 0.5，它们乘积的平均是 0.25。不是“每个结果都等于 0.25”，而是分布倾向改变了。

金属：颜色较亮，粗糙度适中

C++ · 对照你的项目变量名
color albedo = color::random(0.5, 1);
double fuzz = random_double(0, 0.5);
sphere_material = make_shared<metal>(albedo, fuzz);

每个颜色分量落在 [0.5,1)，避免金属太暗。fuzz 在 [0,0.5)，让小金属球有不同程度的反射模糊。fuzz=0 时反射方向不额外扰动；越大，倒影越粗糙。

玻璃：用折射率而不是随机表面色

C++ · 对照你的项目变量名
sphere_material = make_shared<dielectric>(1.5);

这里 1.5 是简化空气/玻璃场景中使用的折射率参数，不是透明度 150%，也不是半径。第 11 章材质会依据正反面选折射比，判断全内反射，再用 Schlick 近似随机选择反射或折射。

教材的玻璃衰减为白色 (1,1,1)，表示没有在材质中加入吸收着色。你看到的玻璃颜色主要来自它反射、折射了哪些环境，而不是代码直接给它涂了一层蓝色。

动手实验：从棋盘看到随机球群

俯视场景生成器：每次换一组随机数

俯视布局示意，不是光线追踪结果。蓝色=漫反射，橙色=金属，绿色=玻璃；灰色环标示右侧排除区。这里使用固定的 JavaScript 随机算法，方便重复实验，不保证与 C++ std::rand 的具体布局相同。

先看三颗大球的相对位置，再看小球中心怎样落进格子。关闭留白，对比右侧金属球周围的变化。同一个种子会给出同一个布局，方便做有控制的比较。

本互动把“布局随机”与“材料随机”分开组织，避免开关留白时把后续球全部打乱。教材 C++ 共用一个随机数序列，分支里还会继续消耗颜色和 fuzz 的随机数，所以删除一次调用也可能改变后面整幅场景。

14.1⑦ 三颗主角球与最终相机

C++ · 对照你的项目变量名
world.add(make_shared<sphere>(point3(0, 1, 0), 1.0,
    make_shared<dielectric>(1.5)));
world.add(make_shared<sphere>(point3(-4, 1, 0), 1.0,
    make_shared<lambertian>(color(0.4, 0.2, 0.1))));
world.add(make_shared<sphere>(point3(4, 1, 0), 1.0,
    make_shared<metal>(color(0.7, 0.6, 0.5), 0.0)));

三颗球半径都是 1、中心高度都是 1，所以球底位于 y=0。中心球展示玻璃，左球展示漫反射，右球展示接近镜面的金属。注意“左、右”这里先说世界 X 坐标，最终照片里的位置还由相机决定。

C++ · 对照你的项目变量名
cam.vfov = 20;
cam.lookfrom = point3(13, 2, 3);
cam.lookat = point3(0, 0, 0);
cam.vup = vec3(0, 1, 0);
cam.defocus_angle = 0.6;
cam.focus_dist = 10.0;

相机站在 (13,2,3)，离地稍高，从斜侧面看原点；20° 是较窄的视角；0.6° 是较小散焦角，不像第 13 章 10° 的夸张演示。

为什么 focus_dist=10，而 lookat 距离不是 10？

|lookfrom−lookat| = √(13²+2²+3²) = √182 ≈ 13.490738 focus_dist = 10 因此原点并不在对焦平面中心；焦平面在到原点之前。

第 13 章已经把“朝向”和“对焦距离”分开。这里是一个具体应用：你可以瞄准原点，却把比较靠近相机的区域设为焦点。

右侧大球中心 Q=(4,1,0) 的轴向深度约为 dot(Q−C,−w)≈9.488，与 10 比较接近。这个数帮助理解构图：清晰区域更偏向前面的金属主角附近，而不是机械地对在原点。

14.1⑧ 从一条光线到一个像素：完整工作链

先用生活里的话说：拍一张合照时，我们不能只问一个小朋友“你看到了什么”。每个像素要问很多次；每次还会沿着光的路线问不同物体：“你又看见了谁？”最后把答案加起来，求一个平均。
main 创建世界。随机球的位置、半径、材质在这里确定，渲染期间不再重新随机摆放。
相机初始化。根据 vfov、位置、朝向、对焦距离计算视口、像素间距与圆盘。
选一个像素。对它重复 samples_per_pixel 次，每次生成一个随机相机样本。
找最近交点。world.hit 遍历物体，逐步缩小允许的 t 最大值，保留最近命中。
询问材质。漫反射选新方向；金属反射并按 fuzz 扰动；玻璃随机反射或折射。
继续追踪或结束。深度用完返回黑色；射向天空则返回天空渐变色；某些材质分支拒绝散射也返回黑色。
把沿途衰减乘回来。每一次返回都乘上该次材质 attenuation。
累加后平均，再输出。线性颜色先求平均，之后才做 gamma 处理和整数转换。
一条样本的路径： 相机 → 棕球 → 地面 → 天空 假设各段衰减：A=(0.4,0.2,0.1)，B=(0.5,0.5,0.5) 天空颜色：S=(0.8,0.9,1.0) 样本颜色：A*B*S=(0.16,0.09,0.05) 像素线性颜色 = 所有样本颜色之和 / 样本数

本例是帮助你跟踪乘法，不表示每条路径只反弹两次。max_depth=50 是递归次数上限，不要求每条光线都走满 50 次；而且当前实现深度耗尽先返回黑色，这种截断会损失长路径贡献。

完整 main.cpp：先跑预览，再追求封面质量

下面是和你项目命名对齐的完整入口。先使用 400 宽、20 样本、20 深度验证构图；教材的最终图参数是 1200 宽、500 样本、50 深度。先确保所有材质和相机功能已经存在。

C++ · 最终场景 main.cpp（预览参数）
#include "rtweekend.h"
#include "hittable_list.h"
#include "sphere.h"

int main() {
    hittable_list world;
    auto ground = make_shared<lambertian>(color(0.5, 0.5, 0.5));
    world.add(make_shared<sphere>(point3(0, -1000, 0), 1000, ground));

    for (int a = -11; a < 11; ++a) {
        for (int b = -11; b < 11; ++b) {
            double choose_mat = random_double();
            point3 center(a + 0.9 * random_double(), 0.2,
                          b + 0.9 * random_double());
            if ((center - point3(4, 0.2, 0)).length() > 0.9) {
                shared_ptr<material> sphere_material;
                if (choose_mat < 0.8) {
                    color albedo = color::random() * color::random();
                    sphere_material = make_shared<lambertian>(albedo);
                } else if (choose_mat < 0.95) {
                    color albedo = color::random(0.5, 1);
                    double fuzz = random_double(0, 0.5);
                    sphere_material = make_shared<metal>(albedo, fuzz);
                } else {
                    sphere_material = make_shared<dielectric>(1.5);
                }
                world.add(make_shared<sphere>(center, 0.2, sphere_material));
            }
        }
    }
    auto glass = make_shared<dielectric>(1.5);
    world.add(make_shared<sphere>(point3(0, 1, 0), 1.0, glass));
    auto brown = make_shared<lambertian>(color(0.4, 0.2, 0.1));
    world.add(make_shared<sphere>(point3(-4, 1, 0), 1.0, brown));
    auto shiny = make_shared<metal>(color(0.7, 0.6, 0.5), 0.0);
    world.add(make_shared<sphere>(point3(4, 1, 0), 1.0, shiny));

    camera cam;
    cam.aspect_ratio = 16.0 / 9.0;
    cam.image_w = 400;            // 先预览；教材最终图用 1200
    cam.samples_per_pixel = 20;  // 先预览；教材最终图用 500
    cam.max_depth = 20;          // 先预览；教材最终图用 50
    cam.vfov = 20;
    cam.lookfrom = point3(13, 2, 3);
    cam.lookat = point3(0, 0, 0);
    cam.vup = vec3(0, 1, 0);
    cam.defocus_angle = 0.6;
    cam.focus_dist = 10.0;
    cam.render(world);
}

-Iproject/head 告诉编译器到哪里找头文件，-O2 打开优化，> 把标准输出保存为 PPM 文件。进度信息用 std::clog，通常走标准错误流，所以仍显示在终端。

不要把调试文字用 std::cout 混进图像数据，也不要使用 2>&1 把错误/进度信息并进 PPM。正常文件前三行类似 P3、400 225、255，后面是颜色数值。文件未写完就打开，看到的不完整图片不能说明渲染失败。

性能实验：为什么最终参数这么慢？

先用生活里的话说：一张照片像一张问卷。像素越多，需要填的格子越多；每格问得越多，总问题数越多；每个问题还要走访很多球。三种成本会叠加。
主射线样本数 = 图像宽 × 图像高 × 每像素样本数 教材最终参数：1200 × 675 × 500 = 405,000,000 即 4.05 亿条从相机出发的样本射线，还没计算后续反弹。 预览参数：400 × 225 × 20 = 1,800,000 即 180 万条主射线样本。 仅主射线数量比：405,000,000 / 1,800,000 = 225 倍

每次找交点，目前的 hittable_list 都要遍历所有物体。用 N 表示物体数、B 表示平均实际处理的路径段数，大致成本是 W×H×SPP×B×N。这是帮助理解增长趋势的粗略模型，不是准确计时公式。

把宽度翻倍且保持宽高比，高度也翻倍，像素数就变成 4 倍。再把样本数翻倍，主射线数量变成 8 倍。max_depth 翻倍则不一定让耗时翻倍，因为很多路径早就离开场景了。

主射线数量计算器

固定 16:9，高度按 C++ 的整数截断计算。柱状图比较当前设置与 400×225×20 的基准；图形采用对数刻度以容纳跨度，真实倍数以数值为准。这里不预测运行分钟数。

阶段宽度 / 样本 / 深度主要看什么
检查编译与方向200 / 5 / 10有没有物体、相机是否看反
预览构图400 / 20 / 20位置、材料、对焦
减少噪点800 / 100 / 50反射、玻璃、散焦边缘是否稳定
最终输出1200 / 500 / 50高分辨率和较低噪声，耗时显著增加

对于通常的独立蒙特卡洛样本，噪声的标准差大致按 1/√N 下降。要把噪声幅度降到一半，常常需要约 4 倍样本，而不是 2 倍。这个关系依赖样本分布与方差条件，不能保证每个像素都严格遵守。

玻璃球为什么像飘着？以及其他常见疑问

玻璃下面阴影弱，不一定就是相交算法坏了

本场景主要由天空环境照亮。透明球会让许多路径经折射继续接收到天空亮度，因此不像不透明球那样简单阻断。阴影较弱、接触感不强，在这个模型和照明条件下可能是正常现象。

但不能推导出“真实玻璃没有阴影”或“只要是玻璃，漂浮一定正常”。光源大小、方向、折射、焦散、地面接触、采样质量都会影响外观。先检查几何位置，再检查材质和光照路径；大地面球的弯曲也可能让某些远处小球并非严格接地。

为什么我和教材的球颜色、位置不完全一样？

随机数发生器、种子、调用顺序不同都会改变场景。C++ std::rand 的具体序列也不要求跨平台一致。要对比某次修改，可以固定种子和调用顺序；如果要跨平台逐位复现，则需要明确随机算法等更多条件。

为什么每次路径都随机，球却不应该移动？

场景随机只发生在创建 world 时；像素、镜头、材质方向的随机发生在渲染采样时。若你把“创建球”放进每个像素的循环，得到的是不断变化的场景平均，已经不是这本书的最终场景。

现象优先处理
编译找不到 dielectric先补第 11 章类；附录提供当前接口的复习代码
相机没有 image_width 成员本项目叫 image_w
相机没有 focus_dist 成员当前相机还没升级到第 13 章
程序很久没结束先降分辨率与采样，确认用了 -O2；检查终端剩余扫描行
PPM 文件无法识别检查文件头、是否混入日志、是否已经输出完成
球黑得不自然深度是否太小；散射是否失败；颜色平均和 gamma 顺序是否正确

14.2① 第二本书：给渲染器增加新本领

先用生活里的话说：现在你会搭一座只有球的玩具城。第二本书会给你更多积木、会动的玩具、带花纹的墙，还会教你先按街区找玩具，避免每次都搜遍全城。
方向小朋友版解释它解决什么
运动模糊快门打开的一小会儿，玩具正在跑给射线加时间，对运动中的物体采样
BVH先找大箱子，再找小箱子，最后找玩具用包围盒层次减少不必要的物体求交
纹理映射给球贴一张世界地图贴纸让颜色随表面位置变化
Perlin 噪声做连续起伏的云纹、木纹生成比独立随机斑点更连贯的纹理
四边形终于可以摆地板、墙面、灯面增加球之外的平面图元
光源在房间里摆一盏真的灯让某些表面发光，而不只依赖天空
变换把玩具搬动、转向复用物体并改变位置与朝向
体积渲染光线在烟雾里面也会被散射模拟介质内部的散射，而不仅是表面

为什么球变多以后，BVH 很有帮助？

想象 500 个玩具被装进不同箱子。射线连一个大箱子的包围盒都没有碰到，那么箱子里的所有玩具都不用逐个测试。BVH 把这种“先排除大组”的思路递归组织起来。

它不是保证每次永远只做 log₂N 次计算；场景分布、包围盒重叠、构建方法和射线方向都会影响效果。但比当前无条件遍历所有球，通常能大幅减少相交测试。

14.2② 第三本书与三个值得理解的延伸

第三本书更关心“该把样本花在哪里、怎样正确计算它们的贡献”。同样数量的射线，如果更多射向真正重要的方向，可能得到更稳定的图像。这涉及概率密度、重要性采样、光源采样等基础，不是简单把循环次数调大。

三角形：模型为什么能从球变成人物？

许多三维模型把表面切成大量小三角形。会与一个三角形求交只是开始，还要加载顶点数据、处理法线与纹理坐标、组织大量面片。三角形网格和 BVH 往往需要一起考虑。

阴影光线：直接问“能不能看见灯？”

在表面点朝选定光源点发一条探测射线，若中间没有遮挡，就可以计算相应直接照明贡献。对点光源与面积光源的采样方式不同，硬阴影和软阴影也不同。

不能只给当前每次命中随手加一个“可见就变亮”的常数。要结合光源强度、表面响应、几何关系、采样概率，并避免与其他路径估计重复计算。玻璃遮挡也不能一概当作完全不透明。

并行：叫更多人一起算，但先约定谁算什么

一种方式是按行、块或像素分工；另一种方式是对同一个固定场景做多份独立采样，最后合并。如果每个工作进程用不同种子重新生成随机球，最后平均的会是多个不同场景，物体位置会“鬼影重叠”。所以场景随机与渲染采样随机必须有清晰边界。

正确合并线性颜色： 若每份样本数相同：C = (C₁+C₂+…+Cₙ)/N 若样本数不同：C = (n₁C₁+n₂C₂+…)/(n₁+n₂+…) 最后一次 gamma 处理，再写图像。

不要直接平均已经 gamma 校正、截断到整数的 PPM 像素。例如线性颜色 0 与 1 的平均是 0.5，之后做本项目的平方根变换约为 0.707；如果先各自开方再平均，只得到 0.5，明显不同。

如果按两两合并，8 份结果依次变为 4 份、2 份、1 份。每一级都要维护正确样本权重；数量不是 2 的幂时，剩余分支也不能丢。共享 std::rand 的调用顺序在并行中还会变得不稳定，实际实现应为各工作单元设计独立的随机状态。

附录：当前项目缺少的玻璃积木，怎样补齐？

以下是第 11 章的复习代码，方便你核对最终场景的依赖。详细原理请结合已有的 第十一章 HTML 阅读。先把 refract 放到 vec3.h 的向量工具函数区，再把 dielectric 放到 material.h、material 基类定义之后。

展开：折射辅助函数 refract
C++ · vec3.h 工具函数
inline vec3 refract(const vec3& uv, const vec3& n, double eta) {
    double cos_theta = std::fmin(dot(-uv, n), 1.0);
    vec3 perpendicular = eta * (uv + cos_theta * n);
    vec3 parallel = -std::sqrt(std::fabs(1.0 - perpendicular.length_squared())) * n;
    return perpendicular + parallel;
}
展开：适配 r.Dir() 的 dielectric 类
C++ · material.h 玻璃材质
class dielectric : public material {
public:
    explicit dielectric(double refraction_index) : ri(refraction_index) {}

    bool scatter(const ray& r_in, const hit_record& rec,
                 color& attenuation, ray& scattered) const override {
        attenuation = color(1, 1, 1);
        double eta = rec.front_face ? (1.0 / ri) : ri;
        vec3 unit_direction = unit_vector(r_in.Dir());
        double cos_theta = std::fmin(dot(-unit_direction, rec.normal), 1.0);
        double sin_theta = std::sqrt(1.0 - cos_theta * cos_theta);
        bool cannot_refract = eta * sin_theta > 1.0;
        vec3 direction;
        if (cannot_refract || reflectance(cos_theta, eta) > random_double())
            direction = reflect(unit_direction, rec.normal);
        else
            direction = refract(unit_direction, rec.normal, eta);
        scattered = ray(rec.p, direction);
        return true;
    }

private:
    double ri;
    static double reflectance(double cosine, double ratio) {
        double r0 = (1 - ratio) / (1 + ratio);
        r0 *= r0;
        return r0 + (1 - r0) * std::pow(1 - cosine, 5);
    }
};

fabs 在这里缓和接近边界时的浮点误差；它不能取代全内反射判断。scatter 必须先检查 eta*sin_theta>1，再决定能否调用 refract。否则“把负数强行变正再开根号”并不能产生物理上正确的折射。

此版本用于本书的简单空气/玻璃边界；复杂嵌套介质需要更完整的介质状态管理。第 12、13 章的相机练习可以先用漫反射和金属，不必等玻璃做完才学相机。

毕业练习：从照抄到自己设计一张图

  1. 改布局。把循环范围从 [−11,11) 改为 [−4,4)，先预测候选格子数，再运行。答案是 8×8=64。
  2. 改概率。想要 50% 漫反射、30% 金属、20% 玻璃，阈值应为 0.5 和 0.8，而不是 0.5 和 0.3。
  3. 改构图。只调整 lookfrom，记录哪些球的遮挡关系变化；再只调整 vfov，比较两种变化。
  4. 改对焦。使用点积计算一颗指定球表面点的轴向深度，设置 focus_dist，观察前后背景。
  5. 研究成本。固定场景，用相同分辨率比较 10、40、160 样本的噪点与耗时，不要同时改所有参数。
  6. 做成作品。先用低分辨率找好机位，再提高采样和尺寸，给最终图片起一个名字。

口头复述题：不看代码，你能描述完整渲染流程吗？

先创建固定世界，再设置相机。每个像素取多次样本，每次随机选像素位置和镜头起点，寻找最近交点，按材质继续散射，直到到达天空、被终止或达到深度上限。沿途颜色衰减相乘，样本颜色在线性空间里平均，最后 gamma 处理并输出。
